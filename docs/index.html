Refresh or Wait? Scoring Which Pages Actually Need a Content Refresh

Hasnain · FlyRank ML Internship Capstone · flyrankrepo1

Abstract. FlyRank's own March 2026 portfolio report covers 341,701 content pieces across 57 brands — far more than any editorial team can manually triage, which is precisely the content-scale problem this capstone tackles at a smaller, reproducible scope: which pages in a library are worth an editor's limited review time this week? Using 30,000 anonymized pages across 32 clients from the FlyRank starter dataset, I built a Logistic Regression model to score pages by their likelihood of being in measured decline, validated it against a fair, non-circular baseline on clients the model never trained on, and audited it for leakage before trusting the result. The model reached a measured precision@50 of 0.76 on held-out clients — well above a fair rule-based baseline (0.30) and the base rate (0.52) — while a more complex Random Forest underperformed it, confirming that added complexity wasn't earning its place here. The output is a ranked, human-reviewed action queue with reason codes, not an automated decision system.

Introduction / Problem

The case study is FlyRank's own content-scale problem. Its March 2026 portfolio report covers 341,701 pages across 57 clients — and even a single one of those clients can hold thousands of pages, far more than any editorial team can manually re-read every month. FlyRank's own findings confirm the cost of not triaging: content peaks around 61–90 days and falls off a cliff by 271–365 days if nobody intervenes, and refreshed old pages show a measured 3.2x health lift in their sample. Someone still has to decide, every week, which pages get that attention first — a content editor with a large library and limited hours can't review everything. The decision this work supports is narrow and concrete: out of an existing content library, which pages should an editor look at first this week? A false negative — missing a page that's genuinely declining — is the more expensive mistake: search visibility, once it starts slipping, gets harder to win back the longer it's ignored. A false positive costs an editor one wasted hour. The goal here isn't to automate refresh decisions; it's to give a human a defensible starting point, at the same content-scale problem FlyRank's own portfolio faces, on a smaller reproducible slice of it.

Data

This paper uses the FlyRank ML Internship starter export — 30,000 anonymized content pages across 32 clients, each row a trailing-90-day performance snapshot with a 30-day-vs-prior-30-day trend comparison built in.

Honest scope note. The full internship track provides access to a ~79M-row production warehouse release on Hugging Face. I set up the data contract for that release (grouped queries, availability filtering, leakage guardrails) but did not have live Hugging Face access or a stored access token in the environment this paper was built in. Every result below is built and validated on the local 30K-row starter export, not the full warehouse — a real limitation, not a rounding error, and it's named again below.

Excluded on purpose: trend_direction and trend_pct define the label itself and are never features. impressions_last_30d / impressions_prev_30d are excluded too — the label is a deterministic threshold on exactly those two numbers, and the leakage audit below shows why that exclusion mattered. No client names, URLs, or private query text appear anywhere in this paper or its source notebooks — all identifiers are pre-anonymized hashes.

Methodology

Label: is_declining_label = (trend_direction == "down") — a rule-derived proxy on measured impression change (54.2% of pages), not a hand-tagged outcome.

Features: 18 numeric signals (search volume, competition, CPC, word/char count, log-transformed 90-day impressions/clicks/sessions/AI-sessions, days with impressions/sessions, content age, days since last update, CTR, average position, engagement/scroll rate, AI traffic share) plus 7 categorical fields (competition level, content type, main intent, age tier, freshness tier, word-count tier, impression tier).

The baseline had a bug worth reporting. My first hand-written rule (declining_and_stale_with_demand) multiplied the label directly into its own score — so it could only ever flag pages that were already true positives by definition, scoring a trivial precision@50 of 1.0. I rebuilt it as a fair baseline — identical staleness + demand logic, label term removed — for an honest comparison. Catching and fixing this is part of the result, not a footnote.

Validation design: grouped 75/25 split by client_id (GroupShuffleSplit), with zero client overlap confirmed between train and test — the model is only ever evaluated on clients it never saw during training.

The leakage confession

Per the internship's own leakage-hunting method: train once without a suspect column, once with it, and watch the score. Adding trend_pct — the label's own definition — back in as a feature sent AUC from 0.616 to 0.987. Adding the raw impressions_last_30d/prev_30d pair pushed it to 0.830. Both confirm why those columns were excluded from the real feature set above, rather than just following a rule blindly.

Two findings worth naming. First, the fair baseline actually scores below the base rate — staleness alone is a weaker signal than intuition suggests, confirmed independently by the paper's own signal audit (staleness-vs-decline came back MIXED, not confirmed, reversing on a thin 181+ day tail). Second, the simpler model won: Random Forest's extra flexibility didn't earn its place on this feature set, so Logistic Regression is the one worth keeping.

Grouped split matters

Re-running the same model under a plain random row-level split (client can leak across train/test) instead of the grouped split gives precision@50 = 0.86, AUC = 0.71 — both higher than the honest numbers above. That gap (≈0.10 precision@50, ≈0.09 AUC) is roughly how much of the random-split score was the model partly recognizing a client it had already seen, rather than generalizing to a new one.

Limitations & honest framing

  • Small sample, not the full warehouse. 30,000 pages / 32 clients — directional evidence the approach is worth extending, not a production-scale finding.
  • Observational, not causal. Nothing here shows that refreshing a flagged page causes recovery — only that current signals match the pattern associated with decline in this sample.
  • A rule-derived proxy label, not a human-tagged outcome — is_declining_label is a threshold on measured impression change.
  • Validated on 8 held-out clients. A larger held-out set would meaningfully strengthen confidence in generalization.
  • ~1 in 4 false positives at the top of the queue (precision@50 = 0.76). This is a ranking tool for human triage, not a verdict.

Human review, required before acting

  1. Confirm the decline looks real — not a seasonal dip or a tracking gap inflating the comparison window.
  2. Rule out a technical cause (deindexing, broken redirect, a competitor outranking it) — a content refresh won't fix a technical problem.
  3. Confirm the page's topic is still worth the editorial time — some flagged pages may have lost relevance entirely.
What this should never automate: auto-publishing content changes, auto-deprioritizing pages on a low score, reporting decline_probability to a client as certainty, or comparing raw scores across different clients.

Monitoring triggers

Retrain or re-audit if: monthly precision@50 on a fresh sample drops meaningfully below ~0.76; the reason-code distribution shifts heavily toward categories that were thin in this run; a new client is scored with full confidence before enough of their own history accumulates; or the underlying decline base rate drifts far from the ~52% observed here.
